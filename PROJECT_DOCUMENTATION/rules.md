# Project Rules and Development Constraints — NegoMind AI

## 1. Overview and Enforcement Model
This rulebook establishes the architectural, engineering, security, and operational rules governing all development on **NegoMind AI**.

Every rule is categorized using standard RFC 2119 terminology:
- **[MANDATORY]**: Requirements that MUST be strictly adhered to. Violations introduce regressions, security vulnerabilities, or broken test suites.
- **[RECOMMENDED]**: Architectural guidelines and best practices that SHOULD be followed unless a compelling technical justification exists.

---

## 2. Source-of-Truth Rules

### Rule ST-001: Authoritative Negotiation State [MANDATORY]
- The Python FastAPI backend (`backend/app/services/orchestrator.py`) and persisted database models (`NegotiationModel`, `NegotiationMessageModel`) are the **authoritative sources of truth** for all negotiation states, rounds, turn transitions, decisions, and outcomes.
- Frontend components MUST synchronize with the backend state via API endpoints (`/api/negotiations/{id}`, `/turn`, `/practice-turn`) whenever backend connectivity is available.
- The client-side JavaScript engine in `src/engine/` is strictly a fallback for offline demonstration and MUST NOT override or diverge from backend calculations.

### Rule ST-002: Single-Source Concession Mathematics [MANDATORY]
- All concession calculations, step amounts, percentages, cumulative decay, velocity, and remaining capacity MUST be computed exclusively using `backend/app/services/concession_tracking.py`.
- No separate module or frontend view is permitted to implement ad-hoc concession arithmetic.
- Target positions MUST be resolved through `get_authoritative_target()` to guarantee that offer evaluation, decision logic, and telemetry reports use the identical target value.

### Rule ST-003: Single API Client Layer [MANDATORY]
- All frontend HTTP requests to the backend MUST be routed through `src/services/api.js`.
- Components and custom hooks MUST NOT invoke raw `fetch()` or `axios` calls directly from UI files.

### Rule ST-004: Centralized Authentication Context [MANDATORY]
- User authentication status, bearer tokens, and active profile state MUST be read exclusively from `src/context/AuthContext.jsx`.
- Components MUST NOT independently read, parse, or manipulate token keys in `localStorage` outside of the auth service.

## 3. Architecture Rules

### Rule AR-001: Preserve Frontend/Backend Boundaries [MANDATORY]
- Business logic, pricing limits, multi-variable utility scoring, prompt generation, and database interactions MUST remain within the backend `app/services/` layer.
- The frontend is responsible for presentation, user interaction, animations, and telemetry visualization.

### Rule AR-002: Do Not Introduce Duplicate Negotiation Engines [MANDATORY]
- When enhancing negotiation logic, developers MUST implement changes in the backend Python engine (`backend/app/services/`).
- Do NOT create a third negotiation engine or independent routing system.

### Rule AR-003: Preserve Database Engine Fallback Behavior [MANDATORY]
- All database interactions MUST flow through SQLAlchemy sessions (`SessionLocal` / `get_db`).
- Code MUST NOT bypass `backend/app/database.py` or disable the automatic SQLite fallback logic.

### Rule AR-004: Single Source for PDF & Export Generation [MANDATORY]
- Server-side PDF, CSV, and JSON exports for negotiation history MUST be generated by `backend/app/services/export_service.py`.
- Developers MUST NOT create competing backend export services.

## 4. Negotiation Rules

### Rule NG-001: Strict Constraint Clamping [MANDATORY]
- No agent is permitted to conclude an agreement outside its defined financial boundaries.
- Every offer generated by an LLM or human participant MUST pass through `validate_agent_constraints()`:
  - Buyer offers or accepted terms MUST NOT exceed `maximum_price`.
  - Seller offers or accepted terms MUST NOT fall below `minimum_price`.
- Out-of-bounds proposals MUST be automatically clamped to the hard boundary and recorded with a constraint adjustment note.

### Rule NG-002: Strict Turn-Taking Consistency [MANDATORY]
- Turns MUST alternate sequentially between participating agents.
- In Practice Mode, a human participant MUST NOT take consecutive turns without an AI response, and the AI MUST NOT act when it is the human's turn.

### Rule NG-003: Deterministic Rule Engine Parity [MANDATORY]
- When operating in Normal Mode, `mock_llm_reasoning` and `decision_logic.py` MUST produce compliant `LLMStructuredResponse` objects containing valid `decision`, `offer`, and `reasoning` fields.
- The platform MUST function completely without external LLM API keys.

### Rule NG-004: Finite Deadlock Resolution Attempts [MANDATORY]
- When a deadlock is detected, the orchestrator MUST NOT attempt more than **one (1)** automated compromise resolution.
- If the compromise proposal is rejected or if constraints do not overlap, the session MUST immediately terminate with status `breakdown` or `deadlock`.

## 5. Scenario Rules

### Rule SC-001: Preserve Default Scenarios [MANDATORY]
- The three standard scenarios (`vendor_pricing`, `job_offer`, `project_budget`) in `backend/app/services/negotiation_service.py` and `src/data/scenarios.js` MUST NOT be deleted or renamed.
- Existing boundary values (Vendor: $42k–$50k; Job Offer: $95k–$110k; Budget: $75k–$85k) MUST remain constant to preserve automated test integrity.

### Rule SC-002: Custom Scenario Validation [MANDATORY]
- Custom scenarios created via the Custom Scenario Builder MUST include:
  1. At least two (2) participants with distinct roles.
  2. Defined numerical boundary limits (`min_value` or `max_value`).
  3. A positive `max_rounds` integer (default: 10).
- Unsupported or unvalidated schema fields MUST NOT be persisted into `custom_scenarios`.

## 6. Authentication and Authorization Rules

### Rule AU-001: Never Trust Frontend User ID [MANDATORY]
- Protected endpoints (`/api/negotiations/history`, `/api/negotiations/{id}/detail`, `/api/negotiations/{id}/export`) MUST derive user identity exclusively from the validated `Authorization: Bearer <token>` header.
- The backend MUST NEVER accept or trust a client-supplied `user_id` query parameter or body field without verifying bearer token ownership.

### Rule AU-002: Strict Resource Ownership Verification [MANDATORY]
- A user MUST NOT be permitted to access, view, or export another user's negotiation session.
- Mismatched session requests MUST return `HTTP 403 Forbidden`.

### Rule AU-003: Never Expose Passwords, Secrets, or Real OTPs in Production [MANDATORY]
- Passwords MUST be stored as salted PBKDF2 hashes; raw passwords MUST NEVER be logged or returned in responses.
- API keys, database credentials, and OAuth secrets MUST NEVER be rendered in public endpoints.
- In production deployment, `demo_otp` MUST be removed from API responses; OTP codes MUST be delivered solely via verified email.

## 7. Negotiation History and Export Rules

### Rule NH-001: Preserve Chronological Order [MANDATORY]
- All historical turn transcripts returned by `/detail` or exported to PDF/CSV/JSON MUST preserve strict chronological order sorted by round and timestamp (`round 1, round 2, round 3...`).

### Rule NH-002: Defend Against CSV Formula Injection (DDE) [MANDATORY]
- All CSV export generation in `export_service.py` MUST invoke `sanitize_csv_cell()` on every text cell.
- Any cell value beginning with `=`, `+`, `-`, `@`, `\t`, or `\r` MUST be prefixed with a single quote (`'`) to force plain-text evaluation in spreadsheet applications.

### Rule NH-003: Safe Handling of Incomplete Sessions [MANDATORY]
- Sessions terminating in deadlock, breakdown, or mid-negotiation cancellation MUST be handled safely without runtime exceptions.
- Export files MUST NOT falsely claim that agreement occurred if `status != 'accepted'`.

## 8. API Rules

### Rule AP-001: RESTful Conventions & Status Codes [MANDATORY]
- Resource creation endpoints (`POST /api/negotiations`, `POST /api/custom-scenarios`) MUST return `HTTP 201 Created`.
- Resource not found MUST return `HTTP 404 Not Found`.
- Authorization failures MUST return `HTTP 401 Unauthorized` (missing/invalid token) or `HTTP 403 Forbidden` (ownership mismatch).
- Invalid input payloads MUST return `HTTP 400 Bad Request` or `HTTP 422 Unprocessable Entity`.

### Rule AP-002: Safe Error Messages [MANDATORY]
- Internal tracebacks and raw database exceptions MUST NOT be leaked to client responses.
- The global exception handler in `app/main.py` MUST log the error internally and return a sanitized JSON message.

---

## 9. Database Rules

### Rule DB-001: Non-Destructive Migrations [MANDATORY]
- Schema migrations MUST NOT drop existing tables or delete existing negotiation records.
- Any column additions MUST provide safe defaults (`server_default` or `nullable=True`).

### Rule DB-002: Atomic Transactions [MANDATORY]
- Operations modifying multiple database records (e.g., session state + message logs) MUST be executed within a single transaction with explicit commit and rollback on error.

---

## 10. Frontend Rules

### Rule FE-001: Follow Design System Conventions [MANDATORY]
- All UI components MUST adhere to the established dark theme (`#0C0C0F` background, `#17161B` card containers, `#26242C` borders, `#34D399` Emerald accents).
- Do NOT introduce clashing arbitrary color palettes.

### Rule FE-002: Handle All State Transitions [MANDATORY]
- Every async data view (History, Arena, Scenarios, Dashboard) MUST provide explicit visual representations for:
  1. **Loading State** (Skeleton loader or spinner)
  2. **Empty State** (Clear prompt when 0 records exist)
  3. **Success State** (Loaded data display)
  4. **Error State** (Actionable error message and retry button)

---

## 11. Testing Rules

### Rule TE-001: Mandatory Regression Testing [MANDATORY]
- After any modification to backend routes or services, the full pytest test suite MUST be executed:
  ```bash
  cd "UI DESIGN/backend"
  python -m pytest
  ```
- All 133 tests MUST pass with 0 failures before code is considered ready.

### Rule TE-002: Never Claim Unexecuted Tests Passed [MANDATORY]
- An engineer or AI assistant MUST NEVER report that tests passed unless the test runner was executed and recorded a zero exit code.

## 12. File Modification & Documentation Rules

### Rule FM-001: Inspect Before Modifying [MANDATORY]
- Always read existing file implementations before proposing or applying edits.
- Never blindly overwrite existing source code.

### Rule FM-002: Protect Branding Assets [MANDATORY]
- The official NegoMind AI branding assets (`logo.png`, `logo-icon.png`, `favicon.svg`, `public/logo.png`) and motto (*Think • Negotiate • Grow*) MUST NOT be deleted, replaced, or modified without explicit user authorization.

### Rule FM-003: Keep Documentation Synchronized [MANDATORY]
- When an API route, database schema, or negotiation behavior is modified, the corresponding documentation files in `PROJECT_DOCUMENTATION/` MUST be updated simultaneously.
